# Security is deny-by-default, rate-limited and hardened at the edge, and personal data is erased separately from Offboarding

Authentication, CSRF, CORS, secrets and logging are already decided (ADRs 0006, 0010, 0011, 0012); this records the rest of the baseline.

**Authorization.** Two roles, Member and Admin (exactly one, spec §2A). Every `/api` endpoint requires a session unless it is on an explicit anonymous allow-list: Invitation redeem, sign-in link request and verify, and health. An architecture test fails when an endpoint is neither authorized nor on the list. `/api/admin/*` is guarded by one endpoint-group policy and answers `403` to a non-Admin (ADR 0006). Handlers take the acting `MemberId` and whether they are the Admin; ownership rules (only the Requester edits or cancels a Request, only the Sitter withdraws a claim) live in Domain or Application, not in endpoints. When the caller should not learn that a resource exists, an ownership failure answers `404` rather than `403`.

**Rate limiting.** The built-in ASP.NET Core limiter, per client IP, with state in a SQLite file (amended 2026-10-27). Sign-in link request: 5 per 15 minutes per IP and per email, so a Member's inbox cannot be flooded. Invitation redeem and sign-in verify: 10 per 15 minutes per IP. `POST /api/client-logs` is limited as ADR 0010 requires. Authenticated calls: 120 per minute per Member. Exceeding a limit is `429` ProblemDetails with `Retry-After`. The client IP comes from forwarded headers, trusted only from the configured proxy.

**Browser hardening.** One middleware sets HSTS and the HTTPS redirect in Production, a CSP of `default-src 'self'` with no inline script and `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (the magic-link token travels in the SPA page's query string), and `Cache-Control: no-store` on `/api`. No CORS policy is registered, so cross-origin calls fail by default (ADR 0006).

**Secrets.** Nothing secret in the repo or `appsettings.json`: `dotnet user-secrets` in development, environment variables in production (ADR 0011). The only secret is the email provider key (#23); sessions are server-side, so there is no signing key. GitHub secret scanning with push protection is switched on in the repository settings; a separate scanning job was rejected to protect CI minutes (ADR 0008).

**Scanning.** `.github/dependabot.yml` covers NuGet, npm and GitHub Actions weekly, with minor and patch updates grouped into one PR. CodeQL for C# and JavaScript/TypeScript runs weekly and on pushes to `main`, not on every PR; the PR gate stays `scripts/check.sh`.

**Children.** v1 stores only a child count per Request. Any child data beyond that (backlog #4) needs its own ADR and a privacy review first, and must be visible only to the Requester and the claiming Sitter while the Request is Claimed, never logged, never in email and never in an Admin view. Free-text notes and addresses are treated as sensitive in the same way.

**Offboarding is not erasure.** Offboarding closes the account, revokes sessions and burns the balance, and keeps the Ledger (spec §2A). It does not delete personal data. Erasure is a separate Admin action, available only on a closed Member: it replaces `Email` and `DisplayName` with a tombstone ("Former member"), deletes Request notes and addresses, deletes any outstanding Invitation or sign-in link for that email, and keeps Ledger amounts and ids, because the Ledger is the system of record. Logs are pruned after 30 days (ADR 0010), so they need no separate erasure. Folding erasure into Offboarding was rejected because Offboarding is routine and must stay reversible by a new Invitation, while erasure is irreversible. Erasure itself is a follow-up ticket; this ADR fixes the rule.

**Amendment (2026-10-23).** Sign-out (`DELETE /api/auth/sessions/current`) is also on the anonymous allow-list: it must clear the cookie even when the session has already expired. The architecture test is `EndpointAuthorizationTests`.

**Amendment (2026-10-23).** Rate limiting details: all windows are fixed. The per-email sign-in limit is checked after the address parses and applies to unknown addresses alike, so the `429` reveals nothing about who is a Member. `POST /api/client-logs` is 30 per minute per Member (it is not also counted in the 120). Invitation preview is not limited. Forwarded headers are read only when `ForwardedHeaders:KnownProxies` lists at least one proxy address; with none configured they are ignored, because the middleware would otherwise trust every caller. The `429` body has code `rate_limited`.

**Amendment (2026-10-24).** GitHub secret scanning with push protection and CodeQL need a paid plan on a private repository, so neither is used and `.github/workflows/codeql.yml` is removed. Scanning runs locally inside `scripts/check.sh` (ADR 0015): gitleaks over the working tree in the fast gate; gitleaks over git history, Semgrep CE with rules vendored in `.semgrep/`, `dotnet list package --vulnerable` and `npm audit` in the full gate. `.github/dependabot.yml` stays (Dependabot is free). Semgrep does pattern matching, not CodeQL's data-flow analysis, so it finds less; revisit with a paid plan or a public repo. This supersedes the **Secrets** sentence about push protection and the **Scanning** paragraph.

**Amendment (2026-10-27).** Rate-limit counters now persist (#54), so a restart or deploy no longer resets them. They live in a second SQLite file beside the main database (`<database>.rate-limits`), not in it: a counter write is one atomic upsert per limited request and must never queue behind a Ledger transaction, and the file needs no backup because losing it only resets the windows. It is a second EF Core context, `RateLimitDbContext`, with its own migrations in `Persistence/RateLimitMigrations`, applied at startup with the main ones. This leaves ADR 0004's single-file persistence for business data untouched. The built-in ASP.NET Core limiter is replaced by a small middleware (`UseApiRateLimiting`) over `SqliteRateLimitStore`; limits, fixed windows and the `429` response are unchanged. Keys are stored as SHA-256 hashes because they embed email addresses and IPs. A hit over the limit still increments, and expired rows are purged every five minutes. Sharing counters between instances is not solved: it needs a distributed store, and the whole app is single-instance on SQLite today (ADR 0004).

**Amendment (2026-10-27, #23).** The only secret is still the email credential, now the Gmail app password, held as a Fly secret (ADR 0018). Behind Fly the app trusts Fly's proxy network for forwarded headers instead of one `KnownProxies` address, so limits apply per real client; the exact addresses and header are verified in #149.

**Amendment (2026-10-28).** The per-Member limit (120 a minute) can be overridden with `RateLimits:MemberPerMinute`. Only the e2e stack sets it, because the design-screenshot run drives one Member through hundreds of page loads a minute. Production leaves it unset, so the default applies.

**Amendment (2026-10-27, #149).** `ForwardedHeaders:KnownNetworks` (CIDR ranges) joins `KnownProxies`, and `ForwardedHeaders:ForwardedForHeaderName` names the header to read when it is not `X-Forwarded-For`. Forwarded headers are read when either list is non-empty. On Fly the proxy network is `172.16.0.0/16` and `fdaa::/16` and the header is `Fly-Client-IP`, set in `fly.toml`; `X-Forwarded-For` is not used because a client can send it. Confirm the ranges after the first deploy (runbook in `docs/development.md`) and amend this note if they differ.

**Amendment (2026-10-29, #94).** An accepted Invitation records the accepting Member (`Invitations.AcceptedByMemberId`, set with `ConsumedAt`), and Erasure tombstones the email on the Invitation with that id instead of every consumed Invitation for the email, which also hit a later Member who returned via a new Invitation. No backfill: nothing is in production, so existing development data is wiped.

**Amendment (2026-10-29, #198).** Request notes are defined: optional plain text of at most 500 characters, written only by the Requester, and treated like the exact address (hidden while Posted, shown to the claiming Sitter once Claimed, never in Notifications, logs, Admin views or email). Erasure deletes the notes of every Request the erased Member posted; notes belong to the Requester, so erasing a Sitter-only Member leaves them. Spec §2A and §4.

**Amendment (2026-11-03).** The 2026-10-29 note above was wrong that nothing needs a backfill: an Invitation accepted before `AcceptedByMemberId` existed kept a null id, so Erasure never found it and the erased Member's email stayed in the Invitations list. Migration `BackfillInvitationAcceptedBy` repairs those rows once: an accepted Invitation with no id whose email no Member has (its Member was already erased) gets the tombstone, and the others are linked to the Member with that email created closest to the acceptance.

**Amendment (2026-11-08, #234).** A white-box attack pass against the local stack found that the CSRF check, the `no-store` header and the rate limits matched `/api` case-sensitively and by exact path, while routing ignores case and a trailing slash, so `/API/...` skipped all three. They now match case-insensitively, and the per-IP rules ignore a trailing slash. Request bodies are capped at 256 KiB (`413` `payload_too_large`) because the anonymous endpoints read the whole body before looking at the token and the Machine has 256 MB. An undefined enum number (`"location": 99`) is rejected by the Domain with `invalid_location`. Two findings are open: a timing difference between a Member and an unknown address on sign-in link request (#240, ADR 0012's no-enumeration promise holds for status and body only) and format characters in display names (#241).

**Amendment (2026-11-08, #235).** A repeatable black-box pass complements the white-box one: a fresh agent with no access to the source attacks a throwaway local stack as an anonymous visitor and an ordinary Member, run before each release with `scripts/blackbox-pentest.sh` (`docs/security/blackbox-pentest.md`). Findings are triaged by a person with the code. Isolation is by tool permissions, not an OS boundary.
