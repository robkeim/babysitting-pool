# Feature flags are backend-defined, server-evaluated and runtime-toggleable

Flags are short-lived release and rollout toggles: hide an unfinished slice on `main`, ramp a change to a share of members, or switch it on for named members. They are not co-op rules; a rule that must stay permanent belongs in `CoopSettings` (ADR 0011). The capability is deliberately richer than this project needs, to exercise the pattern end to end.

**Definition.** A flag is declared in code, in one registry in the Application layer: name, default, and the issue that removes it. The backend is the only place flags are defined; the frontend defines none. Domain code never reads a flag. Flags are checked at the API or application edge, and a gated endpoint answers 404 while its flag is off.

**Evaluation.** The backend uses `Microsoft.FeatureManagement` with its `Targeting` filter and a custom `IFeatureDefinitionProvider`. A flag resolves per caller from: a per-member deny list, then a per-member allow list, then role groups, then a rollout percentage. The rollout hash covers the flag name and the member id, so a 10% rollout of one flag selects different members than a 10% rollout of another and the same members are not always the beta testers. A test with two flags at 10% over a fixed set of ids asserts the cohorts differ. Unauthenticated callers have no id to hash and see only flags that are fully on or fully off. Hand-rolled targeting, OpenFeature (it still needs a provider behind it) and a hosted flag service were rejected.

**Runtime store.** Overrides (enabled, rollout percent, allow and deny lists) live in a SQLite table and are read through a short cache that a write invalidates, so a change needs no restart. Configuration (`Features__<Name>`) only seeds the initial values. Admins change flags through `GET` and `PUT /api/admin/feature-flags` (ADR 0014 authorization applies). An admin screen is a later slice.

**Frontend.** `GET /api/feature-flags` returns the flags already resolved for the caller as `{ name: boolean }`, works before sign-in, and supports ETag and 304. The SPA reads it with TanStack Query (ADR 0003), refetching every 60 seconds and on window focus, and exposes `useFeatureFlag("name")`. No targeting logic ships to the browser and no vendor SDK is added.

**Tests and agents.** Backend tests replace the flag provider in the test host's DI. Frontend unit tests wrap components in a test provider with explicit values. E2E uses `POST /api/test/feature-flags`, mapped only in the `E2E` environment (ADR 0004). Because that endpoint changes who sees what, it is protected in layers rather than by obscurity: the API refuses to start in Production if the `E2E` environment or an `E2E:Token` is present; every call must carry the token, compared in constant time, and answers 404 without it; the endpoint is excluded from `openapi.json`; and a test asserts a Production host returns 404 for it. Moving all test-only endpoints into a `BabysittingPool.TestSupport` project referenced only by the E2E host, so Production does not contain the code at all, is a follow-up, as is applying the token to the existing clock and outbox endpoints.

**Retirement.** Adding a flag opens its removal issue, and the registry comment cites it. Once the flag has been fully on in production, one slice deletes the code path, the registry entry, the tests and, by migration, the store row. Nothing enforces an expiry date.

**Amendment (2026-10-25).** The backend slice settled details this ADR left open. A flag's settings are `enabled` (a master switch: off means off for everyone), `rolloutPercent`, `allowedMemberIds`, `deniedMemberIds` and `roleRollouts` (a list of `{ role, rolloutPercent }`, role `Member` or `Admin`; a list, not a map, because the Postman generator invents keys for a free-form map and ADR 0006 needs deterministic output). `Features__<Name>` seeds a row at startup only when the flag has none, and a name that is not in the registry stops startup. The cache lives 5 seconds and every write drops it. `PUT /api/admin/feature-flags` takes the flag's name in the body and replaces its settings whole. A gated endpoint's 404 has code `feature_off`.


**Amendment (2026-10-25, admin screen).** The admin screen is at `/admin/feature-flags`, linked in the nav for Admins only. Each flag is a form over the whole settings (master switch, rollout percent, a rollout percent for each of the two roles, allow and deny lists as member ids one per line) that saves with `PUT /api/admin/feature-flags`. The list is read in one page; the API never returns a next cursor.

**Amendment (2026-10-29, operator toggles).** A flag declared with a `null` removal issue is an operator toggle: it is not a rollout and nothing retires it. It exists so an Admin can change how the whole app behaves at runtime, and to show the flag machinery working in a demo. The registry comment says why it stays, the admin screen shows "Operator toggle: stays for good" in place of the removal issue, and `removalIssue` in the API is nullable. The first is `vacationMode` (ADR 0017), off by default.

**Amendment (2026-10-29, #101).** The follow-up is done. All test-only endpoints (`/api/test/*`, including the clock, members, sessions, settle and the outbox at `GET /api/test/outbox`) live in `BabysittingPool.TestSupport`, which only the E2E host (`BabysittingPool.E2E`) references, so the Production image contains none of that code or `Microsoft.Extensions.TimeProvider.Testing`. The E2E host runs the API through `ApiHost` with hooks and forces the `E2E` environment. Every `/api/test` endpoint now needs `E2E:Token`, not only the flag override, and the CSRF header exemption for `/api/test` is gone: callers send `X-Requested-With` like the SPA. The Production start guard stays as a second line, and a test asserts the API assembly does not reference the test support. `GET /api/dev/outbox` remains for Development only.
