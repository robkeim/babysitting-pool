# Time-driven changes are applied by one idempotent Settle run, persisted not derived

Expiry, Payout and Demurrage are applied by a single `Settle` use case that reads `now` from `TimeProvider` and takes no timestamp. In production an in-process `BackgroundService` with a `PeriodicTimer` (about every 60s) runs it, and the Admin-only `POST /api/admin/settle` (ADR 0006) calls the same use case and returns counts. The hosted service is disabled by configuration in tests and E2E, which move the `FakeTimeProvider` and call Settle directly. There is no external scheduler or distributed lock: SQLite already means one host. Within a run the order is Expire, Payout, Demurrage.

Expiry is a persisted transition, not a read-time derivation, because the refund is a Ledger entry and the Ledger is append-only. Between ticks the claim handler checks the clock against the stored Claim Cutoff and rejects late claims with 422, and read models project an overdue Posted Request as Expired, so the user-visible behavior is correct without waiting for the tick. The Claim Cutoff is stored as an instant on the Request when it is posted or edited, so later changes to the configurable setting never move a promised window.

Each Request and each Member is settled in its own transaction (ADR 0004). A failure or a `Version` conflict is logged and skipped, then retried on the next tick; one bad row never blocks the rest. Idempotency is state-driven for Expire and Payout (only Posted or Claimed Requests past their trigger are selected) and constraint-driven for Demurrage: each demurrage Ledger entry records its weekly boundary, and a unique index on (Member, boundary) makes a double charge impossible. We rejected a run log or watermark because it is a second source of truth that can disagree with the data.

Demurrage is charged at a global weekly boundary (default Monday 00:00 in the co-op time zone), not on a per-Member rolling anchor. The effective grace is therefore 21 to 28 days, which we accepted for a single testable instant per week. After downtime every missed boundary is applied in order, each evaluated as of its own time. Settle writes no notifications; Notifications are out of v1.
