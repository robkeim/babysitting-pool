# Frontend i18n uses react-intl with hand-authored key-based catalogs and a runtime Ünïcödé Tëst transform

The frontend uses react-intl (FormatJS). Messages are ICU MessageFormat, held in one flat, hand-authored `en-US.json` of `key → ICU string`, which is the source of truth. Keys are dotted and prefixed by feature slice (ADR 0005), for example `requests.list.empty`, with `common.*` for shared strings and `error.<code>` for backend error codes (ADR 0006). Adding a Language is a new `<tag>.json` plus one registry entry. There is no extraction step. `id` is typed as `keyof typeof enUS` through the `FormatjsIntl.Message` augmentation, so a missing key fails the build. `en-US` is bundled eagerly as default and fallback; every other Language is a lazy chunk loaded by dynamic `import()`.

Ünïcödé Tëst is a runtime pure function over the English catalog. On activation it parses each `en-US` message with `@formatjs/icu-messageformat-parser`, rewrites only literal elements, wraps the message once with `⏩ … ⏪` and padding, and passes the resulting ASTs to `IntlProvider`. It lives in its own lazy chunk, so production downloads it only on the explicit URL override. Padding tiers (added length): up to 10 characters +200%, 11-20 +100%, 21-30 +80%, 31-70 +60%, over 70 +30%, taken from the upper end of the W3C/IBM text-expansion averages so it stresses layouts instead of averaging them. The tiers are one constant table.

Gaps are caught by `formatjs/no-literal-string-in-jsx` and `no-literal-string-in-object` at error level in ESLint, a `scripts/check` step that compares every non-English catalog's keys to `en-US`, requires an `error.<code>` entry for every backend code and parses every message as ICU, and the Ünïcödé Tëst E2E pass.

We chose react-intl over Lingui and react-i18next. Lingui compiles messages at build time with no runtime parser, defaults to source-text IDs, and would need explicit IDs, losing its main ergonomic advantage. i18next needs a plugin for ICU. react-intl is natively ICU and key-based, and it accepts pre-parsed ASTs, which is exactly what a runtime transform needs.

We rejected generating the Ünïcödé Tëst catalog at build time. The transform is cheap at a few hundred messages, and a generated file adds a drift check and commit churn for no user-visible gain. The output depends only on the English string, so nothing can go stale. If it ever proves slow, caching it behind a CI drift check remains possible without changing the library.
