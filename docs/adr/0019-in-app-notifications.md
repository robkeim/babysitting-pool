# In-app Notifications are persisted until dismissed, delivered over SSE and hidden behind a flag

Members learn of a Posted Request or a Claim inside the app, without reloading (#137). This records the decisions; the first slice (#152) builds persistence and the list API, with no live stream or UI yet.

**Transport.** Server-Sent Events, built in the next slice. The flow is one-way, server to browser, over the existing single origin and cookie session (ADR 0006), and `EventSource` reconnects by itself. WebSockets were rejected as two-way machinery for a one-way need, and polling as the fallback only if SSE proves unworkable behind Fly's proxy (ADR 0018).

**Persistence.** A Notification is a row, so a Member sees what they missed while away; a live-only stream would lose it. The row holds ids, the kind, a timestamp and a small payload: the Area and start time for `request_posted`, the Sitter's id for `request_claimed`. No address, free text or name (ADR 0014). Rows are written in the same SQLite transaction as `AddPostedAsync` and `SaveClaimedAsync` (ADR 0004): a rolled-back Post or lost claim race leaves none. The Posted fan-out is added with the Post in that same `SaveChanges`, which EF sends as one batch; hand-written SQL is not allowed outside migrations (ADR 0004).

**Audience.** `request_posted` goes to every open Member except the Requester, Dormant Members included, because a Notification is how a lapsed Member finds out there is work. Closed Members are skipped: they cannot sign in, and Erasure would delete their rows anyway. `request_claimed` goes to the Requester only. No other event notifies; in particular Settle writes none, so ADR 0007 stands unchanged.

**Dismissal.** Dismissing hard-deletes the row. There is no read state and no `dismissed_at`: a Notification stays until the Member dismisses it. `DELETE /api/notifications/{id}` is idempotent (204 also for an id already gone) and answers 404 `notification_not_found` for another Member's id; `DELETE /api/notifications` dismisses all of the caller's own.

**Backstop.** Settle deletes Notifications older than 90 days (`CoopSettings.NotificationRetention`), so ones nobody dismisses do not accumulate. Erasure (ADR 0014) deletes all of the Member's Notifications.

**Flag.** Everything is behind the `notifications` flag (ADR 0016), removed by #160. The endpoints answer 404 `feature_off` while it is off. Rows are written regardless of the flag, so switching it on shows what happened before; the domain never reads a flag. If a rollout needs a quiet start, the 90-day sweep bounds the stored backlog.

**Amendment (2026-10-27, live stream, #153).** `GET /api/notifications/stream` is a `text/event-stream` response authenticated by the session cookie; it answers 401 signed out and 404 `feature_off` while the flag is off. OpenAPI cannot model it, so it is excluded from `openapi.json` and this note is its contract. It opens with the comment `: connected`, then sends `event: notification.created` (data: the list item shape), `event: notification.dismissed` (data: `{ "id" }`) and `event: notifications.cleared` (data: `{}`), plus a `: heartbeat` comment every 30 seconds while idle. Events carry no `id:`, and there is no `Last-Event-ID` replay: on reconnect the client refetches the list. An in-process broadcaster keyed by Member id holds one bounded queue per connection (a Member may have several). After the Post or Claim transaction commits, the handler publishes through `INotificationPublisher`; a failure is logged and loses nothing, because the rows are stored. A connection that falls 64 events behind is closed so it reconnects and refetches, rather than blocking others. The dismiss endpoints publish `dismissed` and `cleared` to all of the caller's connections, other tabs included. Rate limiting counts the stream once, when it opens, in its own per-Member bucket (30 a minute) instead of the 120 a minute shared by other calls, so reconnecting is not starved by them. Because the broadcaster lives in memory, a second instance would need a shared bus (ADR 0018 runs one).

**Amendment (2026-10-27, #154): the bell.** The bell sits in the navigation (the bottom bar on mobile, the top bar from `lg`) and opens a popover panel; its badge counts the Notifications loaded, with a `+` when more pages exist. Opening the panel or clicking a row dismisses nothing. Copy is built on the frontend from the kind and payload. A row's current state is derived from lists the app already has, since the row stores ids only: a Posted row is stale ("No longer available", no link) once the whole open list is loaded and its Request is not on it; a Claimed row takes its date and the Sitter's name from My Requests, and falls back to generic copy when the Request is not on the loaded page. To name the Sitter without a Member-lookup endpoint, `RequestView` gains `sitterDisplayName`, set when the Requester lists their Requests (`GET /api/me/requests`) and null otherwise; it follows the Requester's existing right to know their Sitter (spec §4.6).

**Amendment (2026-10-29, #155): live wiring.** While signed in with the flag on, the bell opens one `EventSource` on `/api/notifications/stream` and closes it when the bell unmounts. `notification.created` adds the row to the cached list (ignoring an id already there), refetches the open list and My Requests that a row's state is derived from, and shows a toast for six seconds: a `role="status"` line with the Posted copy, or the generic Claimed copy because the Sitter's name is not known until My Requests reloads. The toast announces and nothing more; the row stays until dismissed. `notification.dismissed` and `notifications.cleared` edit the cache so other tabs and devices follow. The stream replays nothing, so when it reopens after an error the list is refetched from `GET /api/notifications`, replacing the cache; the first open does not refetch. Playwright runs the stack with `Features__notifications=true`.

**Amendment (2026-10-29, #156): cancelled claims.** A third kind, `request_cancelled`, goes to the Sitter when the Requester cancels a Claimed Request. It carries the Request id and its start time, no address or name. `SaveReleasedAsync` writes it in the cancel's own `SaveChanges` when the Request ends Cancelled with a Sitter still set (a withdrawal clears the Sitter, so it notifies nobody) and returns it for the handler to announce. Offboarding a Requester stores the row through the same path but does not push it live; the Sitter sees it on the next list fetch.
