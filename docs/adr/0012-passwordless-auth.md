# Authentication is passwordless: single-use links, hashed at rest, and server-side sessions

Both the Invitation and the sign-in link are 256-bit random secrets (base64url). Only a SHA-256 hash is stored, so a database leak yields no usable link; a hash is enough because the secrets are high-entropy and short-lived. Each is single-use: consuming one sets `ConsumedAt` in the same transaction that creates the session or the Member, and an expired, consumed or unknown secret is the same `422` (`invitation_invalid`, `sign_in_link_invalid`) so a response does not reveal which. Lifetimes are `CoopSettings` (ADR 0011): Invitation 7 days, sign-in link 1 day.

The links open SPA pages (`/invitation?token=…`, `/sign-in/verify?token=…`) that POST the secret to the API, rather than being API GET URLs. A GET that consumes a secret is consumed by email scanners and link previewers before the person clicks it. The SPA removes the token from the address bar after reading it.

Requesting a sign-in link always answers `202`, whether or not the email belongs to a Member, and sends nothing for an unknown or closed one. This removes account enumeration at the cost of a person with a typo waiting for an email that never arrives, which the page text anticipates.

Sessions are rows (hash of a random cookie value, member, last used), not self-contained signed tokens, so sign-out and Offboarding can revoke them. They slide: a session is valid until 30 days after it was last used, and `LastUsedAt` is only rewritten when it is more than an hour old, so reads do not write on every request. The cookie is named `session` (HttpOnly, SameSite=Lax, Path=/, Secure except in Development and E2E, where Safari would drop it on `http://localhost`). Cookie, same origin and CSRF header are as in ADR 0006; the header check is now implemented as middleware on state-changing `/api` calls (except `/api/test`).

`Member` and its `Email` are new persistence tables; `Email` is unique among Members that are not closed, so a person who was offboarded can be invited again as a new Member (spec §2A). Credit Accounts keep no foreign key to Members yet because existing read-side tests seed accounts alone; the key arrives with the first feature that needs it.

`IEmailSender` is an Application port. Development and E2E use the fake outbox (kept in memory, logged, readable at `GET /api/dev/outbox`, which is not in the OpenAPI document). Production has no provider yet (#23), so the Production registration throws when asked to send: bootstrap then fails the start, which is the honest state until a provider is chosen. The bootstrap Admin Invitation is issued at startup when there is no Admin Member and no live Admin Invitation, using the same Application handler as any other Invitation. The Admin Invitation is refused when an Admin exists, enforcing "exactly one Admin" in one place.

Development seed data is written by an Infrastructure seeder rather than through Invitations, because the seeded balances (0.0 and 25.5) are not reachable through the Starting Balance alone. It is idempotent by email and Development-only. E2E creates sessions through `POST /api/test/sessions`, so the real sign-in path is exercised only by its own journey.
