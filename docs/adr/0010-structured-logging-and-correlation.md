# Logging is structured Serilog with W3C trace correlation, stdout plus a SQLite sink, and a never-log list

The backend logs through `ILogger<T>` in Application and Infrastructure, with Serilog as the provider and message templates with named properties (`"Claimed {RequestId} by {MemberId}"`), never string interpolation. Events are JSON objects whose keys are the template properties, so a request is found by `RequestId = X`; request-wide properties (`TraceId`, `MemberId` once authenticated, `Source`) are attached once as scope. Domain logs nothing: handlers log business outcomes. If Domain ever needs to log, it declares a small `IDomainLog` port with an adapter over `ILogger` in Infrastructure (the architecture tests keep Domain pure until then). Levels: `Error` for unexpected failures (an unhandled exception, a failed Settle row), `Warning` for handled but notable events (a retried `Version` conflict, a rejected client log), `Information` for one line per business outcome (Request posted, Claimed, Completed, Expired, Offboarded, Settle run summary), `Debug` off in production. Expected 4xx outcomes (ADR 0006) are not errors. Serilog request logging writes one line per HTTP request with route template, status and duration, never the raw path, query string, headers or bodies. Event names are PascalCase past-tense; property names are PascalCase and consistent.

Correlation uses the W3C `traceparent` header. The frontend API wrapper (ADR 0005) is the single place that generates a trace id per call and sets it; the backend adopts it (or creates one), puts `TraceId` in the log scope, echoes it in a response header, and includes it in every ProblemDetails body so an error shown to a Member can quote a reference. Each Settle tick (ADR 0007) gets its own trace id. There is no session id: the cookie session value is a secret and cannot be logged, and `MemberId` plus a time range is enough for a co-op this size. Unauthenticated requests (redeeming an Invitation) still carry a `TraceId`. A `SessionId` enricher can be added later in the same place.

Logs go to stdout always (the 12-factor safety net, and the path to a shipper such as Loki or Datadog if we scale) and to a SQLite sink in a separate `logs.db` file so history can be queried with SQL. The sink writes batched in the background (flush every 1-2 seconds) on a bounded queue that drops the oldest events on overflow and never blocks a request; it is never inside a handler's transaction (ADR 0004), and a sink failure never fails a request. Serilog `SelfLog` goes to stderr so a broken sink is visible. Fixed columns are `Timestamp`, `Level`, `Message`, `TraceId`, `MemberId`, `Source`, plus a JSON `Properties` column; `Timestamp` and `TraceId` are indexed. Rows older than 30 days are pruned on the Settle hosted service tick, which also bounds how long a `MemberId` outlives Offboarding. Logs are for debugging only; the Ledger is the system of record. An Admin log viewer is out of scope.

The frontend logs errors, not analytics: uncaught exceptions, unhandled rejections, React error-boundary catches and failed non-4xx API calls. A `logger` module in `shared/` (`error`, `warn`, `info`) writes to the console in development and batches to `POST /api/client-logs` in production, which writes into the same backend log with `Source=Frontend`. The endpoint requires the cookie session and the CSRF header (ADR 0006), is rate-limited, caps payload size and accepts only a fixed schema (message, stable error code, route name, trace id, app version), never free-form objects, so it cannot become a log-injection or data-leak channel. No third-party service.

Never logged: anything about children, magic-link tokens, session cookies, CSRF values and `Authorization`/`Cookie`/`Set-Cookie` headers, email addresses and display names, free-text fields (Request notes, addresses), and request or response bodies. Members appear only as their opaque `MemberId`; Request and Ledger entry ids are fine. This is enforced in layers: (1) a test fails the build on `{@` destructuring in a message template, so only scalar ids and values are logged; (2) a Serilog policy masks properties whose names match a denylist (`Token`, `Email`, `Authorization`, `Cookie`, `Password`, `Note`, and so on) as a backstop; (3) an integration test runs the main flows with an in-memory sink and asserts no captured event contains the known test token, email, display name or note text; (4) request logging uses the defaults above; (5) ESLint `no-console` everywhere except the `logger` module.

We rejected full OpenTelemetry (traces, metrics, exporter) as too much for a toy project; `traceparent` keeps ids compatible so it can be added later. We considered stdout only, a rolling JSON-lines file queried with `jq` or DuckDB, a collector sidecar and a log server (Seq, Loki). The SQLite sink is the chosen option for in-app SQL history; its costs are crash-time loss of the unflushed batch (stdout stays on as the safety net), a schema and pruning code we own, and a local file that does not survive running several instances. Moving to the rolling file or a shipper only changes the Serilog sink configuration, not the logging call sites.

**Amendment (2026-11-10, #274).** Request logging, correlation and the never-log guards are implemented; the SQLite sink is not. The line is `HttpRequestHandled {RequestMethod} {RouteTemplate} {StatusCode} {ElapsedMs}`, with `unmatched` as the route when no endpoint matched (never the raw path), at `Information` and at `Error` only for a 5xx. The response header is `X-Trace-Id`, and the Problem extension is `traceId`. `Source` is `Api` for requests and `Settle` for a Settle tick; `MemberId` joins the scope after authentication. The denylist masks a property whose name ends with a denylisted word (so `NotificationId` is not caught by `Note`). The fake outbox no longer logs the address and link in E2E and tests, only in Development (ADR 0011), because both are on the never-log list.


**Amendment (2026-11-10, #279).** The SQLite sink and its 30-day pruning are deferred until there is real traffic; stdout is the only sink for now. The cost: until it is built, `fly logs` keeps only a short buffer, so log history is lost, and when the sink is built the app owns a schema, pruning code and sink failure modes. The `MemberId` retention bound that the pruning gave is moot meanwhile, since the app stores no log history. Everything else in this ADR stands. Where each part is implemented: Serilog, request logging, `TraceId` correlation and the never-log guards in #274; the `POST /api/client-logs` endpoint in #277; business-outcome log lines in #280; the frontend `traceparent` and error reference in #276; the frontend `logger`, error boundary and `no-console` rule in #278. The SQLite sink, pruning and `logs.db` have no ticket.

**Amendment (2026-11-11, #277).** `POST /api/client-logs` answers `204`. The body is a JSON object of exactly `message` (1-500 characters, no control characters), `code` and `route` (short, restricted charsets), `appVersion`, and an optional `traceId` (32 lowercase hex) for errors outside an API call; any other property rejects the payload. Bodies over 4 KiB are `413`, other rejections `400` `invalid_request` naming the field, and each is logged as `ClientLogRejected {Field} {Reason}` at `Warning` with none of the payload. An accepted report is `ClientErrorReported {ErrorCode} {Route} {AppVersion} {ErrorMessage}` at `Error`, with `Source=Frontend` and the report's `TraceId` in place of the request's, so `TraceId = X` finds the failed call's server lines too. `message` is client text and is not masked: the frontend must not put URLs, tokens or user content in it (#278).

**Amendment (2026-11-11, #278).** The `logger` lives in `src/frontend/src/lib/logger/`. Only `error` reaches the backend, because the endpoint writes every report at `Error`; `warn` and `info` are console-only in development and dropped in production. Production queues reports and sends each as its own `POST /api/client-logs` (the endpoint takes one object) every 2 seconds or at 10 queued, on `pagehide` with `keepalive`, with a 20-entry queue that drops the oldest; a failed send is dropped silently and never logged. The message is sanitized (URLs and emails replaced, control and format characters collapsed, 500 characters), the route is the router's route id, never the concrete path, and the trace id is the failed call's, or else the latest API call's. Wired to `window` `error` and `unhandledrejection`, the router's `defaultOnCatch` (a route component's render error never reaches an outer boundary) plus a root `ErrorBoundary` for the shell, and the API wrapper for 5xx responses and network failures. An error object is reported once, so a 5xx logged by the wrapper is not logged again when it reaches the boundary. `no-console` applies to all of `src/` except the logger module and test files, which spy on the console.
